# 1. Project Overview

계약과 디바이스 정보가 각각 관리되면서 발생하던 교체·회수 업무의 복잡도를 줄이기 위해, **계약과 기기 생애주기를 연결한 운영 시스템을 기획했습니다.**

사내 AI 해커톤에서 운영 데이터를 통합하는 프로토타입으로 1위를 수상한 뒤, 실제 업무를 맡으며 발견한 문제를 중심으로 기능과 운영 기준을 다시 설계했습니다.

현재는 프로토타입 검증을 거쳐 실제 운영에 활용할 수 있도록 데이터 구조를 전환하고 있습니다.

---

# 2. What I Worked On

## 2-1. 계약과 기기 정보 연결

계약별로 출고된 기기의 시리얼을 연결해, 거래처와 계약을 기준으로 현재 사용 중인 기기와 교체·회수 대상 기기를 확인할 수 있도록 구성했습니다.

---

## 2-2. 교체·회수 기준 정리

기기는 검교정 만료일과 USIM 데이터 송수신 만료일 중 빠른 시점을 기준으로 교체해야 합니다.

이 기준을 시스템에 반영하고, 교체 안내 시점과 회수 기한, 미회수 상태 등 실제 업무에서 필요한 처리 기준도 함께 정리했습니다.

---

## 2-3. 계약과 매출 정보 연결

세금계산서 발행 내역만으로는 어떤 계약과 서비스에서 발생한 매출인지 확인하기 어려웠기 때문에, 계약 정보와 함께 아래 데이터를 조회할 수 있도록 보강했습니다.

```text
판매 / 렌탈 구분
서비스 유형
발생주의 매출 여부
매출 귀속 월
```

---

## 2-4. 반복 업무를 줄이는 기능 구성

회수 대상 기기 목록과 거래명세서 파일, 안내 메일 본문처럼 반복해서 작성하던 자료는 시스템에서 생성할 수 있도록 했습니다.

다만 외부로 나가는 메일은 담당자가 내용을 확인한 뒤 직접 발송하도록 해, **자동화가 필요한 부분과 사람이 판단해야 하는 부분을 구분했습니다.**

```text
시스템 생성
→ 담당자 확인
→ 직접 발송
```

# 3. Project Context

기존에는 계약과 기기 정보가 서로 다른 자료에서 관리되고 있었습니다.

특히 한 거래처가 여러 계약을 가지고 있는 경우, **현재 사용 중인 기기가 어느 계약에 속해 있는지, 어떤 기기를 언제 교체하고 회수해야 하는지 바로 확인하기 어려웠습니다.**

교체 업무도 담당자 간 연락에 의존했고, 회수 여부를 지속적으로 확인하는 체계가 없어 기기가 제대로 회수되지 않는 경우도 있었습니다.

처음부터 별도의 시스템을 만들려고 시작한 것은 아니었습니다.

사내 AI 해커톤에서 매출·계약·운영 데이터를 한곳에서 확인하는 대시보드 아이디어를 구현했고, 이후 실제 업무를 담당하면서 **데이터를 한 화면에 보여주는 것보다 먼저 해결해야 할 운영 문제가 있다는 것을 확인했습니다.**

그래서 해커톤 당시의 기능을 그대로 확장하기보다, 계약과 기기의 관계, 교체 기준, 회수 상태처럼 실제 업무에서 필요한 기준을 다시 정리하는 방향으로 프로젝트를 발전시켰습니다.

---

# 4. Main Case

## 계약과 기기 생애주기를 하나의 흐름으로 관리하기

### Challenge

가장 큰 문제는 기기 정보 자체가 부족한 것이 아니라, **기기와 계약의 관계가 명확하게 연결되어 있지 않다는 점**이었습니다.

어느 거래처에 어떤 기기가 나갔는지는 확인할 수 있어도, 여러 계약이 동시에 진행되는 거래처에서는 특정 기기가 어떤 계약에 속하는지 확인하는 데 시간이 걸렸습니다.

여기에 교체와 회수까지 별도의 커뮤니케이션으로 진행되면서, 담당자가 각 정보를 직접 대조해야 전체 상황을 파악할 수 있었습니다.

### Decision

처음에는 필요한 정보를 한 화면에 모으는 방식으로 접근했지만, 실제 업무를 들여다볼수록 **정보를 모으는 것보다 먼저 처리 기준을 정해야 한다고 판단했습니다.**

그래서 기능을 추가하기 전에 먼저 업무의 흐름을 정리했습니다.

```text
계약
↓
기기 연결
↓
교체 시점 판단
↓
출고
↓
회수
↓
이력 관리
```

이 과정에서 교체 안내 시점, 회수 기한, 미회수 상태처럼 담당자마다 다르게 판단할 수 있었던 기준도 함께 명확히 했습니다.

### Action

정리한 업무 흐름을 기준으로 계약별 출고 기기 시리얼을 연결하고, 검교정과 USIM 만료일을 활용해 교체 대상을 확인할 수 있도록 했습니다.

이후 기기 목록과 출고·회수 상태, 거래처, 검교정 정보, 출고일과 회수일 등 실제 운영에 필요한 정보를 조회할 수 있는 프로토타입을 만들었습니다.

프로젝트가 진행되면서 운영팀뿐 아니라 재무팀에서 필요한 정보도 함께 확인했습니다.

그 결과 기기 관리에 그치지 않고 계약번호와 서비스 유형, 판매·렌탈 구분, 매출 귀속 정보까지 연결해 조회할 수 있도록 범위를 확장했습니다.

### Result

프로토타입을 통해 기존에는 각각 확인해야 했던 **계약, 기기, 교체·회수 상태와 이력을 연결해서 관리할 수 있는 기본 구조를 만들었습니다.**

다만 실제 회사 데이터를 적용하면서 새로운 문제가 드러났습니다.

일회용 기기를 포함해 **10만 대가 넘는 데이터**를 스프레드시트 기반 구조에서 처리하기에는 성능과 확장성에 한계가 있었습니다.

단순히 속도를 개선하는 방식으로는 장기적인 운영이 어렵다고 판단해, 현재는 **Supabase에 별도의 데이터 테이블을 구성하고 기존 데이터를 Raw Data로 활용할 수 있도록 마이그레이션하고 있습니다.**

프로젝트는 아직 실제 운영 적용을 준비하는 단계이기 때문에, 회수율이나 업무시간 감소와 같은 운영 성과는 도입 이후 별도로 검증할 예정입니다.

# 5. How I Worked

## 기능을 만들기 전에 업무 기준부터 정리했습니다.

이 프로젝트는 처음부터 완성된 요구사항을 가지고 시작하지 않았습니다.

실제 업무를 맡으며 문제를 발견하고, 그 과정에서 필요한 기준을 하나씩 정리한 뒤 프로토타입에 반영했습니다.

```text
업무 흐름 파악
↓
문제와 예외 상황 정리
↓
운영 기준 정의
↓
요구사항 구체화
↓
프로토타입 구현
↓
실데이터 적용
↓
한계 확인
↓
데이터 구조 전환
```

Claude Code는 아이디어를 빠르게 구현하고 수정하는 데 활용했습니다.

대신 **무엇을 구현할지, 어떤 데이터를 연결할지, 어느 단계에서 사람이 판단해야 하는지는 실제 업무를 기준으로 정했습니다.**

프로토타입을 만드는 것 자체보다, 만들어진 기능을 실제 데이터와 업무 흐름에 적용해 보고 다시 수정하는 과정을 반복하는 데 더 중점을 두었습니다.

# 6. Impact

## 사내 AI 해커톤 1위

운영 데이터 통합 아이디어를 실제 업무 문제를 해결하는 프로젝트로 발전

## 계약과 기기 데이터 연결

계약을 기준으로 기기 시리얼과 교체·회수 이력을 확인할 수 있는 구조 구현

## 운영 기준 정의

교체 시점, 회수 기한, 미회수 상태 등 기존에 명확하지 않았던 업무 기준 정리

## 10만+ 기기 데이터 검증

실데이터 적용 과정에서 스프레드시트 기반 구조의 성능·확장성 한계 확인

## Supabase Migration

실제 운영에 활용할 수 있도록 데이터 테이블을 재구성하고 기존 데이터 마이그레이션 진행

> 현재 실제 운영 적용을 위한 데이터 구조 전환 단계이며, 회수율·업무시간 등 운영 성과는 도입 이후 검증 예정입니다.

# 7. Takeaway

이 프로젝트를 진행하면서 **운영 시스템을 만든다는 것은 기존 업무를 그대로 화면에 옮기는 일이 아니라는 점**을 가장 크게 배웠습니다.

업무를 시스템화하려면 먼저 어떤 상황에서 어떤 판단이 필요한지, 담당자가 무엇을 확인해야 다음 단계로 넘어갈 수 있는지를 명확히 해야 했습니다.

그 기준이 정리된 뒤에야 필요한 기능과 데이터 구조도 자연스럽게 정리됐습니다.

또 프로토타입 단계에서는 잘 작동하던 방식도 실제 규모의 데이터를 적용하면 다른 문제가 생길 수 있다는 것을 경험했습니다.

빠르게 구현하고 끝내는 것보다, **실제 데이터를 적용해 한계를 확인하고 운영 가능한 구조로 다시 설계하는 과정이 더 중요했습니다.**
